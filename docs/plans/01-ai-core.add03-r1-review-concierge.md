## Findings

| ID | Severity | Finding | Recommendation | Section |
|----|----------|---------|----------------|---------|
| C-1 | P0 | **lore-garden Register() API breaks completely.** lore-garden calls `anthropic.Register(anthropic.Config{APIKey: apiKey, BaseURL: baseURL}, "lore-garden")` (and equivalents for openai/google). The plan removes the old `Config` struct with `APIKey`/`BaseURL` fields and replaces it with `ClientConfig` that has only `HTTPClient`. The plan's migration section (4.2) shows the new pattern but does not account for callers that pass a custom `BaseURL` at registration time. lore-garden uses `cfg.BaseURL` from its config file to allow operators to point at custom endpoints. Under the new API, the caller would need to call `ai.RegisterCustomProvider()` to set a custom base URL, but this would conflict with the catalog-loaded provider config for the same name (e.g., "anthropic"). The plan says custom providers overwrite catalog providers (TestCustomProviderOverwritesCatalogProvider), but there's no documented pattern for "I want to use the standard anthropic provider but with a different base URL." | Add a documented migration pattern for callers that customize base URLs. Options: (a) RegisterCustomProvider with the same name as the catalog provider to override it, or (b) a helper like `OverrideProviderBaseURL(name, url)`. The plan should explicitly state that overwriting a catalog provider by name is the intended pattern for this use case and provide a concrete code example. | 4.2 |
| C-2 | P1 | **lore-garden Register() passes explicit API keys that would be lost.** lore-garden passes `APIKey: apiKey` (from Vault/env) directly to `anthropic.Register()`. Under the new model, API keys come from env vars listed in `ProviderConfig.KeyEnvVars`. If the operator stores the key in a non-standard env var or retrieves it from a secrets manager at runtime, there's no way to inject it except via `RegisterCustomProvider` with a direct key. This is supported but the migration path in 4.2 says "No explicit key passing needed at registration time" which is misleading -- it's only true if the key is in the standard env var. | Clarify in Section 4.2 that callers who inject keys programmatically (not from the standard env var) must use `RegisterCustomProvider` with the `APIKey` field, or use `StreamOptions.APIKey` per-call. Provide a concrete code example for the Vault/secrets-manager use case. | 4.2 |
| C-3 | P1 | **Python script still emits `api` and `baseUrl` per model entry.** The `build_chat_catalog()` function at line 544-545 writes `entry["api"] = provider_info["api"]` and `entry["baseUrl"] = provider_info["baseUrl"]` for every model. The plan's Section 3.8 mentions the script must be refactored but provides no detail on what the new script output structure should look like. The script currently outputs `{"lastUpdated": "...", "providers": {...}}` where "providers" is the model data (not provider configs). The new format needs `{"lastUpdated": "...", "providers": {<provider configs>}, "models": {<model data>}}`. The script needs substantial restructuring. | Create a concrete specification or pseudocode for the script changes. The `build_chat_catalog()` function needs to return two separate dicts: provider configs (with apiClientType, baseUrl, keyEnvVars, headers, providerSpecific) and model entries (without api/baseUrl). The existing `NATIVE_PROVIDERS` dict and `OPENROUTER_PROVIDER` dict already have the right data to build provider configs from. The plan should specify where `keyEnvVars`, `headers`, and `providerSpecific` values come from in the script (hardcoded constants, since they're not discoverable from any API). | 3.8 |
| C-4 | P1 | **Embedding model `baseUrl` still emitted by Python script.** The `_embedding_model()` helper at line 596 includes `baseUrl` as a field. The plan says baseUrl is removed from EmbeddingModel but the script migration note in 3.8 is vague ("stop emitting api/baseUrl per model"). The embedding catalog builder needs the same treatment. | Explicitly list `_embedding_model()` as a function that must be updated to remove the `baseUrl` parameter. Also note that `validate_catalog()` (line 694) needs updating since it currently validates the old structure. | 3.8, 6.3 |
| C-5 | P2 | **`GetModel(provider, modelID)` semantics tighten but API unchanged.** lore-garden calls `ai.GetModel(providerName, modelName)` where `providerName` is "anthropic", "openai", etc. The plan says model registry's outer key changes to "strict provider name that must match a registered ProviderConfig." Since the catalog uses the same names ("anthropic", "openai", "google", "openrouter"), this is compatible. However, the plan doesn't discuss what happens if a caller registers a custom provider with a different name (e.g., "my-anthropic-proxy") and registers models under that name. `GetModel("my-anthropic-proxy", "claude-sonnet-4-6")` would work, but `GetModel("anthropic", "claude-sonnet-4-6")` would not find those custom models. This is probably fine but worth noting as a behavioral change: models are now scoped to their exact provider name, not shared across providers using the same API type. | Add a brief note in Section 4.4 that models registered under a custom provider name are NOT accessible via the original provider name. Callers looking up pricing for a model on a custom provider need the custom provider name, not "anthropic". | 4.4 |
| C-6 | P2 | **`PricingKnown` field not on `EmbeddingModel`.** The plan adds `PricingKnown` to both `Model` (Section 3.6) and `EmbeddingModel` (Section 3.11), which is good. However, the `EmbeddingCost` struct has only `PerMTok float64` -- there's no analog to `CalculateCost` for embeddings. The current `embedding_api.go` (line 44) calculates cost inline. If `PricingKnown` is false and `PerMTok` is 0, the inline cost calculation produces 0 -- which is indistinguishable from "this model's cost calculation ran and returned zero." The plan should either document that `PricingKnown` on embedding models follows the same semantics as chat models, or note that callers should check `PricingKnown` before trusting `Usage.Cost`. | Add a note that embedding cost calculation (in `embedding_api.go`) should check `PricingKnown` before computing cost, or at minimum document the intended semantics for consumers. | 3.11 |
| C-7 | P2 | **`Model.Headers` type change breaks lore-garden compilation.** lore-garden imports `ai.Model` (via the public `ai` package re-exports). Changing `Headers` from `map[string]string` to `map[string][]string` is a breaking type change. Any lore-garden code that reads `model.Headers` would fail to compile. Currently lore-garden doesn't appear to access `model.Headers` directly, but any downstream that does will break. The plan mentions using grep to find `StreamOptions.Headers` callers (Section 4.2) but doesn't mention `Model.Headers` callers. | Add `Model.Headers` and `EmbeddingModel.Headers` type changes to the migration grep patterns in Section 4.2. | 4.2 |
| C-8 | P2 | **`GetProviders()` function removed without replacement.** The current `registry.go` exports `GetProviders() []Provider` which returns all registered providers. The plan replaces the provider registry entirely but doesn't mention whether `ListProviderConfigs()` (which returns `[]string` of names, not full configs) is sufficient for all current callers of `GetProviders()`. If any caller iterates providers to check capabilities or API types, they'd need `GetProviderConfig()` for each name. | Verify no downstream callers use `GetProviders()`. If they do, consider adding a `ListProviderConfigValues()` that returns `[]ProviderConfig` (analogous to the old return). | 7.1 |
| C-9 | P3 | **Cohere provider has no `apiClientType` for chat.** In the catalog example (Section 3.8), the "cohere" provider has `embeddingApiClientType` but no `apiClientType`. This is correct (Cohere is embedding-only in this system), but the `ProviderConfig` struct doesn't have any validation or documentation that `APIClientType` can be empty for embedding-only providers. If someone tries to use a cohere chat model, the error path would be: `GetProviderConfig` succeeds, `GetAPIClient("")` fails with "no API client registered for type: " -- which is a confusing error message. | Add a brief comment or validation note that embedding-only providers may have empty `APIClientType`, and consider improving the error message in `Stream()` to say something like "provider %q does not support chat completions (no apiClientType configured)". | 3.3, 3.7 |
| C-10 | P3 | **`ClearProviderConfigs` acquires two locks sequentially.** The implementation acquires `providerConfigMu` then `directAPIKeysMu`. `UnregisterProviderConfig` does the same. This is fine and consistent. However, the comment on `RegisterCustomProvider` (Section 3.9) calls out the lock ordering rationale in great detail, but `ClearProviderConfigs` (Section 3.4) does the same nested locking without a corresponding comment. | Add a brief lock-ordering comment to `ClearProviderConfigs` for consistency. | 3.4 |

## Summary

The plan is thorough, well-structured, and has clearly benefited from multiple rounds of review. The core architecture (separating API client type from provider) is sound and well-motivated.

From the lore-garden downstream consumer perspective, the most critical issue is **C-1/C-2**: the migration path for callers that pass explicit API keys and custom base URLs at registration time. lore-garden does both, and the plan's Section 4.2 migration example ("No explicit key passing needed") only covers the happy path where keys are in standard env vars. The fix is straightforward (use `RegisterCustomProvider` to override) but needs to be explicitly documented with a code example showing the full pattern for callers migrating from the old `Register(Config{APIKey: ..., BaseURL: ...}, sourceID)` call.

The Python script migration (C-3, C-4) remains underspecified despite SR2 flagging it. The plan says "the script must be refactored" but doesn't specify the concrete output structure or which functions need changing. Given that this script is the primary way the catalog gets updated, this gap could block the implementation or lead to a broken catalog.

The remaining findings are moderate-to-minor and should be straightforward to address during implementation.

**Overall assessment:** Ready for implementation with the C-1/C-2 migration documentation as a blocking fix. The architecture is clean and the plan is detailed enough to implement from.
